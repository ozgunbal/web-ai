Postmortem · on-device agent build

Getting a 1.5B-parameter model to speak JSON

Ten rounds of debugging a browser-side LLM intent parser — from a silent config bug buried in a model's own release, through a runtime that fought its own documentation, to a model that quoted our instructions back at us instead of answering them.

Stack: WebLLM 0.2.84 · WebGPU · zod Models tried: gemma-2-2b-it → gemma3-1b-it → Qwen2.5-1.5B-Instruct Fixes shipped: 10

The setup, in one sentence

A React demo app runs an LLM entirely in the visitor's browser via WebGPU, asks it to turn a typed sentence ("transfer $200 to savings") into one JSON object matching a fixed schema, and only then lets a deterministic policy engine decide whether to act on it. No server, no API key — which also means no server logs, no stack traces from a vendor's backend, and no one else's postmortem to read when it breaks. Everything below was diagnosed from inside the browser tab.

The incident log

In the order they actually happened. Each one looked, at first glance, like the same complaint — "the model won't give me JSON" — and each one turned out to be a genuinely different layer of the stack.

infra Symptom — download succeeds, browser throws anyway

Cache.add() encountered a network error

BindingError / NetworkError: Failed to execute 'add' on 'Cache':
Cache.add() encountered a network error
Root cause
The presentation machine had ~2.8 GB of free disk left. Chrome's Cache Storage quota is a function of free disk space, and the 1.9 GB Gemma-2B model download was tripping that ceiling mid-write. Confirmed with df -h, not guessed.
Fix
Downgraded to a 711 MB model and added a proactive navigator.storage.estimate() check that warns before a doomed multi-minute download starts.
model config Symptom — model loads, then refuses to construct

Two settings the model itself shipped in conflict

WindowSizeConfigurationError: Only one of context_window_size and
sliding_window_size can be positive. Got: context_window_size: 4096,
sliding_window_size: 512
Root cause
Fetched the model's own mlc-chat-config.json straight from Hugging Face: it ships with both fields positive. WebLLM's own prebuilt model record for it only overrides one of the two — a real gap in the vendor's shipped defaults.
Fix
Passed { sliding_window_size: -1 } as a per-call override, exactly as the error message itself suggested.
infra Symptom — crashes the instant a real message is sent

A documented feature that doesn't do what its docs say

BindingError: Cannot pass non-string to std::string
at GrammarCompiler.CompileJSONSchema
Root cause
WebLLM's response_format: { type: "json_object" } is documented as "guarantees valid JSON" — but its runtime unconditionally compiles a JSON-schema grammar from a schema string we'd never supplied. Traced to the exact call site in WebLLM's own source, not assumed.
Fix
Dropped response_format entirely. Structural validation moved fully onto our own zod parse-and-reject loop — which, per the original design, was always meant to be the real security boundary anyway.

Root cause

our bug Symptom — failures with zero diagnostic trail

The one thing that actually explains a failure was never kept

Every rejected parse only ever produced the same sentence: "Model output did not validate against the Intent schema after retries." Zod's own error.issues — the exact field, the exact type mismatch — was computed on every attempt and discarded on every attempt.

Fix
Grouped console logging for every attempt (prompt, raw output, extraction result, validation issues), and promoted the real issue detail into the user-facing failure reason instead of a generic string.
model behavior Symptom — plausible-looking JSON, wrong on every field

Reasonable output the schema was too rigid to accept

With real diagnostics finally in place, the next failures turned out to be cosmetic: "amount": "200" as a string, and a dropped rawInputSummary field the model wasn't treating as essential.

Fix
z.coerce.number() for amounts, .default("") for the summary field — deliberately not touching the closed action-type enum or any required transfer field, which stayed exactly as strict.
model behavior Symptom — output degrades from "wrong" to "not JSON at all"

An unfinished thought, cut off mid-object

```json

"Account1234567890, 100.01 — never closes
Root cause
A verbose model front-loading prose before the real answer, hitting the 200-token ceiling from fix 04 before it ever reached a closing brace.
Fix
Raised the ceiling to 400 tokens, added one concrete example JSON object per action type to the prompt, and made extractJson() try every fenced code block in a reply, not just the first.
model behavior Symptom — the model quotes the prompt back instead of answering it

It learned our formatting, not our task

User message:
User input: show me my accounts.
User: show me accounts
…repeated with small variations, for hundreds of lines
Root cause
The literal string "User message: {text}" was being folded into one user-role turn. With no real system role in play, the model had no signal that "User message:" was our formatting convention rather than content worth imitating — so it imitated it.
Fix
Sent instructions and the visitor's actual words as two genuinely separate chat messages — system, then user — with zero hand-rolled labels in either.
The pivot

Round nine came back worse, not better. Same category of failure as round eight, after a fix aimed squarely at that category. That's the signal that a problem has stopped being a bug and started being a ceiling: a 1-billion-parameter, heavily quantized model asked to hold a schema, a retry correction, and a user request in mind at once — and reliably lose track of which one it was supposed to be doing.

The fix wasn't a fix. It was Qwen2.5-1.5B-Instruct — roughly double the parameters, a chat template with a real system-role turn instead of role-folding, and a config that already shipped the window-size setting from incident 02 correctly. Free disk space had also grown to 7.9 GB by this point, removing the original constraint that picked the smaller model in the first place.

our bug Symptom — correct answer, "broken" outcome

The model was finally right. The app wasn't looking.

✓ allowed · list_accounts · {"type":"list_accounts", "rawInputSummary":""}
Approved but could not execute: No [data-agent-action="list_accounts"]
element found on current screen.
Root cause
The demo only mounts one screen's DOM at a time. The model parsed the request correctly and the policy engine approved it correctly — the visitor was simply looking at a different screen than the one the action lived on.
Fix
An intent→screen map, consulted before execution: the agent now switches screens itself, waits a frame for React to mount it, then acts — the same principle a human assistant follows without being told.

What carries over

Five things worth saying out loud to anyone else about to put a small model in front of real users.

01 A vendor's docs describe the intent, not always the runtime.

Twice — the window-size conflict, the response-format crash — the fix came from reading WebLLM's actual source at the exact call site, not from its documentation. Both bugs were shipped in a widely-used library, not exotic edge cases.

02 Every rejection needs to carry its own reason forward.

The single highest-leverage change in this whole log was incident 05, and it was purely diagnostic: keep the data a validator already computes, instead of collapsing it into one static sentence. Every fix after it got faster because of it.

03 A model imitates the shape of what it's shown, not just its content.

Incident 08 wasn't a prompting problem in the "try different words" sense — it was a structural one. Labels meant for a human reader ("User message:") read as formatting instructions to a model with no other way to tell instruction from content apart.

04 Getting worse after a targeted fix is itself the answer.

Nine straight rounds of narrowing, sharper, more targeted fixes — and round nine came back with the same failure family, undiminished. That pattern is the signal to change what's being fixed, not how hard.

05 "The model answered correctly" and "the task succeeded" are different claims.

The very last bug wasn't a model problem at all. Once the intent layer was solid, the next failure was waiting in the application layer that assumed the model would only ever be asked about whatever was already on screen.
